# Migrating to nelli 0.9.1

A patch release with behaviour changes, so it gets a note. It ships the fixes
of the wiring audit that ran after the 0.9.0 tag (RFC-0005, handoff entry
"2026-11-03 — Wiring audit") and the fixes of the multi-round code review of
the same surface (`docs/rfc/0005-review.md`). Read `docs/migration/0.9.0.md`
first if you are coming from 0.8.0; this note covers only what moves between
0.9.0 and 0.9.1. The full list is in `CHANGELOG.md`.

A few things break a build (§4): an exhaustive `case` over `ReplayStatus`, a
positional two-name unpack of `CachedRaised`, the finding sink
(`consumeSymexFindings`, and `recordSymexFinding` with one argument), a
comparison of `replayWitness`'s result against a `ReplayOutcome`, and the
internal exports the review removed. Everything else compiles before and
after, which is why this note exists.

## 1. Verdicts that move

Three of these were regressions in 0.9.0 against 0.8.0. Each 0.9.0 answer
below was wrong; 0.9.1 gives the right one.

| SUT shape | 0.8.0 | 0.9.0 | 0.9.1 |
|---|---|---|---|
| `for x in s` / `for i, x in s` over a seq whose body changes its length (`s.pop()`, `s.add`, `s.del`) | `sxUnknown` | clean false `sxSat` after the loop, clean false `sxUnsat` in `except AssertionDefect` | `sxRaised AssertionDefect` where Nim raises it; declines where `assert` may be compiled out |
| a user exception type (or `RegexError`) through `symexFindAllWitnesses` / `symexForAll` | `sfUnsat` | `sfUnknown` | what `symexFind` decides |
| a replay that reaches the target, then `quit`s, crashes or hangs, through `assertCoveredBy` / `symexForAll` | declined | the witness was run in your process, which it ended or hung | never run in your process (§2) |

These were wrong on 0.8.0 too:

- an inert `{.symexOpaque.}` callee compiled with `nanChecks` or `infChecks`
  on: a target in `except FloatingPointDefect` was a clean false `sxUnsat`;
- a statement-position opaque or foreign call whose later argument writes a
  variable an earlier one reads (`opq(v div b, bump(b))`): a clean false
  verdict either way;
- a deleted `{.symexTransparent.}` call whose argument carries a check
  (`trv(v div b, 0)`): a clean false `sxUnsat`.

The code review found more verdicts that were wrong on 0.8.0 and 0.9.0 alike.
In each, the 0.9.1 answer is the one native Nim gives:

- **An inner `try` inside an `except` handler.** A `try` in a handler body
  claimed every caught entry at its depth, so when one `try` caught two raises
  from separate statements, the handler's continuation was walked twice:
  `except ValueError: try: inc y; except CatchableError: discard; inc x`,
  then a target on `x == 2`, was a clean false `sxSat`. The handler runs once
  per path, and 0.9.1 does not reach the target. This is the one to look for
  first: it is a trusted `sxSat` on a program that cannot reach the target.
- **An `elif` condition with a bounds check or a call.** `if i >= s.len:
  symexTarget("past-end") elif s[i] == 3: discard` was `sxRaised IndexDefect`,
  `trusted()`, with witness `s = @[]`, `i = 0`, where native Nim reaches the
  label; a label target was a false `sxRaised`, and a `var`-seq call in the
  `elif` gave a clean false `sxUnsat`. A later condition's preamble now runs
  only where that condition is tested.
- **`succ`, `pred`, `inc`, `dec`, `+=` and `-=` on an enum, `char` or range.**
  A target on `OverflowDefect` was a clean false `sxUnsat`, and a label behind
  the wrapped value (`succ('\xff')`) a false `sxSat`. `inc`/`dec`/`+=`/`-=` on
  a range variable raised `RangeDefect` in the model where native Nim raises
  `OverflowDefect`. All now raise `OverflowDefect` where Nim does; a type whose
  bounds are not read declines.
- **A finding from an earlier `assertCoveredBy`** appeared in a later
  `symexForAll` report (§3).

These were wrong only in machinery 0.9.0 introduced:

- **A regex PCRE would reject.** 300 nested groups were `sxSat "a"`,
  `(?:[a-z]){1700}|b` was `sxSat "b"`, and `except RegexError` was `sxUnsat`,
  all trusted. More than 250 levels of nesting now raise `RegexError`; a pattern
  whose compiled-size bound passes PCRE's 65536 code units, or nears its
  workspace, is `sxUnknown`. The bound is an upper bound, so a pattern whose bound
  passes the limit declines even where PCRE would accept it.
- **A variant construction after a branch.** `if b > 3: let p = Pkt(opcode: op,
  tag: gN); if p.tag == 5: <label>`, with `gN` a global nothing writes, was
  `sxSat` with an empty `pathTaint` and `trusted()`. The taint a decline queued
  landed on a sibling path or none. The path now carries `scSpurious`, so a hit
  is replayed before it is reported, and `sxUnknown` if the replay refutes it.

If a pin of yours asserted one of the 0.9.0 answers, it asserted a wrong one.

A hand-built result is also no longer trusted: `ReplayStatus` has a new zero
value, `rsUnsettled`, and `trusted()` is false for it. A `SymexFinding(status:
sfSat)` or `SymexResult` you construct without a `soundness` was `trusted()`
before and is not now. Set `soundness` explicitly.

## 2. Things that run, or no longer run, in your process

**`fn` runs in more cases** (the execution contract of 0.9.0 §1.1, widened).
A clean winning path whose witness renders lossily (a parameter shape that is
`wfLossy`, such as a `seq` of tuples inside a `ref`, or a run whose extraction
substituted a value, `feExtractionFailed`) is now replayed once, in a child,
before it is reported. In 0.9.0 it was reported `trusted()` without anything
having run it. If `fn` must never run at a call site, `SymexSettings(replay:
false)` still opts out (0.9.0 §1.3), and such a winner is then
`rsUnconfirmed`.

**`ReplayStatus.rsUnconfirmed`.** A lossy clean winner that no replay
confirmed (refuted, timed out, crashed, declined, or replay off) keeps its
status, `sxSat` or `sxRaised`, but is not `trusted()`, and a `feReplay*` hint
says why. Code that branches on `r.status == sxSat and r.trusted` (as 0.9.0's
checklist advises) needs no change. Code that branches on status alone sees no
difference; code that checks `r.trusted` alone sees `false` where 0.9.0 said
`true` for such a winner.

**`Soundness.witnessUnsafe`.** A confirmed claim whose replay child reached
the target and then exited, was signalled or ran past `replayTimeoutMs` sets
it, with a `feReplayCrashed` or `feReplayTimedOut` hint. The claim stands. Its
witness is never run in your process:

- `symexForAll` does not use it as a seed;
- `assertCoveredBy(fn, target)` with no `testFn` passes on the replay's
  evidence, without splatting;
- `assertCoveredBy` with a `testFn`, or on an `sxRaised` claim, fails with an
  `AssertionDefect` whose message starts `assertCoveredBy: the symex witness
  is known to end or hang the process that runs it`. The coverage of that
  `testFn` cannot be checked in-process. If you hit it, the SUT has an input
  on which it ends its process after the target: that is usually the finding.

`witnessUnsafe` is wider than the wiring audit set it: any replay that does not
finish sets it, whether or not it confirmed. An `rsUnconfirmed` witness whose
replay ended its child before the target is `witnessUnsafe` too, and is not run
in your process. A child that started and whose exit status was lost
(`SIGCHLD` ignored in your process, or the status reaped by another wait) is
treated the same way, and is a hit if it wrote one: it was reported as a
refused replay, and as exit code 0, before.

**`assertCoveredBy` reads `trusted()`.** An untrusted (`rsUnconfirmed`) witness
is run in your process, unless its replay ended the child, and a hit proves
coverage. A miss is reported as unconfirmed, as an `sxUnknown` is, and not as
`testFn`'s failure; `acceptUnknownAsCovered = true` downgrades it. Only a trusted
witness that `testFn` misses blames `testFn`. `symexForAll` seeds only
witnesses it may run in your process.

**The replay child, and the files it leaves.**

- A child that writes more than 4096 bytes of report, or bytes that are not a
  report, is killed and read as timed out, which is run-dependent (nothing it
  wrote is trusted). A child that floods used to make the host re-decode its
  whole report on each read, overrun `replayTimeoutMs`, and with no timeout
  grow without bound.
- The re-executed child's files (`-d:nelliReplayReexec`, and the default on
  Windows) live in a private directory created for the spawn, with the files
  created exclusively. Before, they had predictable names in the shared
  temp directory. If you cleaned up `nelli-replay-*` files in the temp
  directory, look for a per-spawn directory instead.
- On Windows the child inherits only the NUL handle. Before, it and the SUT
  inherited every inheritable handle of your process.
- `NELLI_REPLAY_CHILD` in your environment no longer matters: it is a per-spawn
  marker with a nonce, and one the program merely inherited is ignored. It used
  to refuse every replay, so a stale one cost precision silently.

## 3. What a finding now tells you

`SymexFinding` gains `hints` (every entry of the run's error list `gaps`
leaves out, the replay outcomes among them) and `diagnostics` (the raises the
run reached that did not decide the verdict). Every report format prints
them. If you parse `ofJson`, each symex finding now has `"hints"` and
`"diagnostics"` arrays (`[]` when empty). `ofGithubAnnotation` adds a
`::notice` per hint. Output for a finding with neither is unchanged.

The 0.9.0 note's Windows advice (§5a, §7: look for the `feReplayDeclined`
hint that starts `replay not marshallable:`) now works through `symexForAll`
and `symexFindAllWitnesses`, via `SymexFinding.hints`.

A finding also carries `bounds`: the `ResourceBudget` the verdict was decided
under, since an `sfUnsat` is a proof only within it. Every renderer shows it,
and the soundness rendering gains the two fields no renderer showed:

- `ofText` and `ofJunit` (its `<system-out>`): a `bounds <field>=<value> ...` line
  under every finding except `sfNotApplicable` and `sfReplayMiss`, and
  `witnessUnsafe=true` and `runDependence={...}` in the finding's head when set.
  A parser of that text that expected the lines after a finding to be only
  `hint` and `also raised` lines will see `bounds` first.
- `ofJson`: `"bounds"`, an object of the budget's fields, on the same findings;
  inside `"soundness"`, `"witnessUnsafe"` (a boolean) and `"runDependence"` (an
  array of member names, such as `"rdReplay"`). Existing keys are unchanged.
- `ofGithubAnnotation`: a `::notice title=symex bounds::` line for an `sfUnsat`
  ("within ..."), and a `::warning title=symex witness unsafe::` line for a
  witness that is not run in your process.

**Findings come back by value.** The thread-local finding sink is gone. A
finding belongs to the call that made it:

- `assertCoveredBy` returns its `SymexFinding` (a `seq[SymexFinding]`, one per
  target, for the multi-target form). The value is discardable, so a call
  used as a statement compiles as before.
- On failure it raises `SymexCoverageDefect`, an `AssertionDefect`, so an
  `except AssertionDefect` still catches it, with `findings` carrying them.
- Inside a `forAll` the finding is also on the run's `Report.symexFindings`, one
  entry per `fn`, call site and target. The entry is the most severe finding
  made under that key (a trusted coverage failure outranks everything), so a
  later passing example does not hide an earlier failure. A nested `forAll`'s
  findings reach the enclosing run's report.
- Outside a `forAll`, in a plain test body, a `fuzz` or concolic harness, or a
  thread the property started, nothing is recorded; `droppedSymexFindings()`
  counts how many were dropped on the thread. The return value and the defect
  are the only channel.
- Before, a finding from an earlier `assertCoveredBy` on the thread could
  appear in a later `symexForAll` report. It cannot now.

`SymexResult.fromCache` is always `false`, and always was: `symexFind` has no
cache. If you branched on it, that branch never ran. The cache-hit flag is
`SymexFinding.fromCache`.

## 4. Compile breaks

- `ReplayStatus` gains `rsUnconfirmed`, tail-appended: an exhaustive `case`
  needs an arm.
- `CachedRaised` gains a third field, `choices`. `let (raw, gaps) = hit`
  stops compiling; name the fields or add the third.
- `ReplayStatus` also gains `rsUnsettled`, as its *first* member, so it is the
  zero value (a record nobody settled is not trusted). An exhaustive `case`
  needs that arm as well, and the ordinals move: `rsNotNeeded` is 1 and
  `rsConfirmed` 2, where 0.9.0 had 0 and 1.
- `consumeSymexFindings` and the `symexFindings` variable are removed, and
  `recordSymexFinding(f)` is now `recordSymexFinding(origin, f)`, with
  `origin: FindingOrigin` (`site: string`, `fnId: string`). All were in
  `nelli/engine/types`, so `import nelli` saw them. Read the finding from
  `assertCoveredBy`'s return value, `SymexCoverageDefect.findings`, or
  `Report.symexFindings`. A harness that opens its own engine frame uses
  `pushEngineFrame()` and `popEngineFrame()` (or `withEngineFrame`).
- `replayWitness` returns a `ReplayResult`, not a `ReplayOutcome`: compare
  `r.outcome`, and read `r.detail` for how the child ended. The type's fields
  are private, so you cannot construct one; `ReplayResult()` is the replay that
  did not run (`roDeclined`). `ReplayOutcome` moved to `nelli/smt/replayresult`
  and `nelli/symex` still exports it, but `roDeclined` is now its first member:
  the other members' ordinals each move up one.
- `saveSymexWitnessImpl`, `saveSymexVerdictImpl` and `saveSymexRaisedImpl` now
  return a `bool` (true when they wrote the entry), marked `{.discardable.}`. A
  call used as a statement compiles as before.
- `symexCacheKey` gains a second trailing parameter, `buildFlags`, after
  `replayMode`. A positional call that passed `replayMode` is unaffected.
- Internal exports removed, for anyone who imported them directly:
  `lastReplayDetail` (`nelli/smt/replayproc`), `symexQueryTimedOut` and
  `symexNativeStackCut` (`nelli/smt/runtime`). The run's run-dependence is
  `Soundness.runDependence`, set where the run ends; read it off the result, not
  the thread.
- `SymexProgram` gains a field, `implDigest`. Its constructors are macro-built;
  a hand-built one without it keys no callee source.

## 5. The cache

Every 0.9.0 entry is orphaned (walker version 272, soundness encoding version
3, and a new key prefix): the first run after the upgrade is cold. The key is
now `sx2:` plus the SHA-256 of its canonical form, where it was `sx:` plus a
SHA-1, so no earlier key is read. The key gains `|rm=<mode>` (how
the build replays: `fork`, `reexec` or `none`, `+panics` under `--panics:on`)
and, for a program with user exception types, `;uxh=[...]`. A database shared
between a Linux and a Windows build, or a `--panics:on` build and another,
therefore keeps separate entries for each. A replay left undecided for a
reason of the run (a timeout, the replay's memory limit, a child that could
not be started, a runtime hook the host had set) is no longer cached as
`:unk`, so such a verdict is recomputed on each run until one decides it. A
claim that is `rsUnconfirmed` or `witnessUnsafe` for such a reason is not
cached either: a hit would run in your process a witness whose replay hung
or lost its child on another host.

Two more parts join the key, and they split entries that used to be shared:

- `|bf=<flags>`: the runtime checks this build compiles in (assertions and each
  check switch), `-d:danger`, `-d:release`, the memory model, the backend,
  `--exceptions`, `--threads`, `--stackTrace` and `--lineTrace`. A debug
  build's replay-confirmed raise is no longer served as trusted to a
  `-d:danger` build whose `fn` does not check. `--panics:on` stays in `|rm=`.
  `--cc`, `--cpu` and `--os` are not keyed.
- `;impl=<digest>`: a SHA-256 over the source of every user routine `fn` reaches
  natively, with the check options each was compiled under. Editing the body of
  a `{.symexOpaque.}` or `{.symexTransparent.}` callee, a declined call or a
  routine the IR holds only by name now changes the key. It is absent when there
  is no such routine. Not keyed: the external body of an `importc` or `dynlib`
  routine (its name, signature and pragmas are), the overrides of a method `fn`
  calls (those the walk dispatches over are in the IR; their own callees are not
  followed), the target of a call through a proc value, and the compiler's
  `lib/` tree (the `nim=` part covers the toolchain). Changing a body no key
  covers still serves the old run's result. Delete the entry.

The macros `symexCacheKeyForFn`, `saveSymexWitness`, `loadSymexWitnesses`,
`saveSymexVerdict` and `loadSymexVerdict` now register the SUT's methods before
they parse, as `symexFind` does. For a SUT that calls a method they used to key
the undispatched program wherever no other entry had registered the methods:
a key `symexFindAllWitnesses` never wrote, and one that depended on expansion
order. They now share its key.

**Raised records.** The index for a SUT's `sxRaised` findings is now under
`:raised2`, where it was `:raised`, and a save is all-or-nothing: an empty index
first, then every per-type record, then the real index. Every earlier raised
record is a miss, then a cold run. The old `:raised` entries are not removed
and are never read; delete them if the database's size matters. A save that
fails part-way reads back as a miss, never as a partial set. Concurrent writers
to one directory database, or a power loss without fsync, can still interleave.

**The soundness encoding** is `3:<pathTaint>:<runTaint>:<replay>:<unsafe>`, plus an
optional sixth field for `runDependence`, written as the enums' ordinals. A
version-2 record cannot say whether an unconfirmed witness ended its child, so
it is a miss. Those ordinals are now pinned at compile time: a nelli release
that changes one bumps the version, so a stored record is never read as a
different status.

If you call `symexCacheKey` yourself, it gains a trailing `replayMode`
defaulting to this build's; pass it only to compute another build's key.

## 6. Known limitation

On macOS and musl, a `feReplayCrashed` hint reads "exited the process with
code 0" for any `quit(n)`: the forked child's exit hook there is `atexit`,
which is not told the status. The verdict is right; only the code in the
message is not. Other open items are in
`docs/rfc/0016-native-parity-hardening.md` §5.8, INT-22 to INT-27.
