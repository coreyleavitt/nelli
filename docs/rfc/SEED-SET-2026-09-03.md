# The 0006–0012 seed set — composition rationale

Composed 2026-09-03 from a post-0005 architecture survey (five parallel
explorations: shrinking architecture, replay durability, concurrency and
temporal surface, public-API ergonomics, three-engine integration).

This file holds what no individual seed owns: **why these seven, why grouped
this way, and in what order.** Deliberately unnumbered — a `NNNN-` prefix
would make quipu parse it as an eighth RFC.

## The one-sentence finding

nelli's founding thesis — *all nondeterminism is recorded choices, therefore
shrinking is free* — is only half-exploited, and three of the four structural
seeds below are consequences of pushing it to its conclusion.

The engine records choices but cannot run that direction backwards (0006). It
owns input nondeterminism but not scheduling, time, or failure (0009). It
constructs a trace on every stateful run and then discards it (0007).

## Why these merges

Grouped by **shared mechanism**, never by theme. Three merges happened:

**0006 absorbs the shrink-quality benchmark** — not as a component but as
slice 1. There is no measurement of shrink quality anywhere in the repo, so
the RFC could neither demonstrate improvement nor rule out regression. The
instrument lands before the change. It carries a second payload: whether
nelli's linear-plus-spans sequence shrinks `flatMap` and `filter` measurably
worse than a sample tree is currently an unanswerable question, and after
slice 1 it is a number. If that number is bad it spawns its own RFC — a
shrinker representation change is not a slice of 0006.

**0008 merges three survey candidates** (evidence ledger, statistical
distribution contracts, suite budget scheduler) because they are one mechanism
from three sides: a per-property evidence record that persists across runs.
`cover` writes a statistical verdict into it; the scheduler reads it to
allocate and writes back what it spent; the CI gate diffs it. Splitting them
would mean designing the record against a single consumer — which is exactly
how a shared abstraction freezes into the shape of consumer one. The
scheduler is the second consumer that validates the interface, and should be
spiked early even though it ships last.

**0010 merges the ergonomics items** under one root cause rather than four
patches. Nim object literals zero-fill; nelli's settings types carry non-zero
defaults; the documented idiom is the object literal. The library has met this
four times and answered it four different ways — including a bespoke
single-field sentinel and a hand-written fourteen-branch merge. The fix worth
making is the general one.

Two merges were considered and **rejected**: 0007 into 0009 (simulation needs
traces, but that is a dependency, not a merge — 0007 stands alone and upgrades
three existing subsystems), and 0011 into 0012 (both add new property kinds;
that is a theme, not a mechanism).

| 0011 | effect-annotations | symex | small | 0005 (hard) |

Five are `core` — the PBT engine itself, which had never been the subject of
an RFC. 0001–0005 were all symex, fuzzer, or packaging. That is itself worth
noticing: the substrate everything is layered on has been evolving without a
design record.

## A second axis: when a consuming team hits these

The seeds are grouped by mechanism. There is an orthogonal axis worth holding
alongside it — **the phase of a consuming project's life in which each gap
bites** — because it does not line up with the mechanism grouping and it is
what a downstream team actually experiences.

- **Adoption phase.** 0010. The object literal is what a team copies on day
  one; the defect is aimed at the least experienced user at the moment they
  are deciding whether to adopt, and it degrades trustworthiness of failures
  and termination of shrinking — the two things that judgement rests on.
- **Active-development phase.** 0006. Generator churn is continuous while
  types are still being designed, so the regression DB evaporates fastest
  exactly when the application is moving fastest. Also 0006's third symptom:
  *production handed us this input, minimize it* is the most-wanted workflow
  nelli does not have.
- **Maturity phase.** 0007, 0008, 0011, 0012. Liveness properties, assurance
  evidence, proven effect annotations and complexity bounds all matter once a
  system is real enough to have queues, retries, CI gates, and SLAs.
- **Systems phase.** 0009. Only a project with genuine concurrency needs it,
  and such a project needs it badly.

This axis reinforces the mechanism-derived order below rather than fighting it
— 0010 first, 0006 next — which is mild evidence the grouping is right.

## Recommended order

1. **0010** first, alone. It is small, it carries a live user-facing defect
   (the README's own example silently disables the flakiness detector and
   makes shrinking unbounded), and it touches configuration surfaces that
   every later RFC will add fields to. Fixing the policy before four RFCs add
   settings is materially cheaper than after.

2. **0006**, and not close on merit. The only item that is simultaneously a
   fix for five documented defects, a prerequisite for value-level evidence in
   0008, an enabler for value-level fuzz crossover, and a single optional
   field on a type that already has the exact precedent (`display`).

3. **0007** — small, and upgrades stateful/bmc/bisim rather than adding a
   fourth thing. Also a hard prerequisite for 0009, so building it now avoids
   inventing a sixth private history type later.

4. **0008** — mostly harvests evidence the engines already compute.

5. **0011 and 0012** are independent and small; either can be slotted whenever
   0005 closes (0011) or as a palate cleanser (0012).

6. **0009** last, and not started while any of the above is open. It is a
   quarter, not a sprint.

## Where 0005 sits

0005 is currently the only unblocked item on the board and has no named
downstream consumer. **0011 is one** — it is entirely a consumer of sound
`sxUnsat`, which is precisely the half of 0005's soundness rule identified as
missing. If 0005 wants a motivating application to design against, it is
`checkRaises`.

## What was deliberately left out

- **`docs/MODAL_PBT_PLAN.md`** (solver-driven constrained generation; 12–18
  weeks + a Lean 4 mechanized proof) — an existing standing plan awaiting a
  downstream trigger, not a gap found by this survey. Unranked here because
  ranking it would misrepresent it as new work.
- **Full design-by-contract** (`requires`/`ensures`, auto-derived properties
  from signatures). A different library. 0011 is the one slice of it that
  earns its place, because the specification is already written.
- **Async/`Future` property support.** Zero usage anywhere in the library
  today. It is a decision to make, not necessarily work to do, and it is
  entangled with 0009's "what is a task" fork.
- **Field-level strategy annotations on derived types.** Real want, own
  mechanism, named as out-of-scope in 0010 so it does not drift in.
- **The positive adoption case** — that one property text escalates through
  random → fuzz → symex without a rewrite, that `arbitrary(T)` makes the
  marginal property nearly free, that `assertCoveredBy` keeps a coverage claim
  true as code moves, that `sxUnsat` lets a team *close* a question under
  bounds rather than sample it forever. All true, none of it belongs in a seed:
  an RFC argues a gap, not a strength. It belongs in `README.md` and the
  onboarding docs, and its absence there is a documentation task, not an RFC.

## Status of this set

Seeds, except 0006. Every one carries an explicit §Open questions block naming
the forks that must close before `/tdd`. The scope statements are deliberately
narrow and the out-of-scope lists deliberately explicit, because the failure
mode for a seed set this size is drift, not under-ambition.

**0006 went through `/architect` round 1 on 2026-09-03** and is now a `draft`.
Two things there bear on this file:

- **Its size is `L`, not the `medium` in the table above.** Round 1 found that
  `parse` propagation misses the two surfaces that produce most user strategies
  — `derive.nim`'s `arbitrary(T)` and the `given` DSL's multi-binding macro —
  both of which need parse *synthesis*, not field propagation. That is roughly
  half the work and it was invisible in the seed.
- **It may spawn an RFC-0013 (`T` codec), which would change this set's shape
  and order.** Value-level DB persistence — the fix for 0006's symptom 2 — needs
  a general `T` serializer that is effectively a second derive macro. 0006 §7
  recommends splitting it out, partly because 0008's value-level evidence is a
  natural second consumer, so the codec would be designed against N=2 rather
  than frozen onto 0006. That decision is open and is Corey's.

The "one-sentence finding" above survives round 1 intact. What did not survive
is 0006's account of *how* the engine fails: replay clamps rather than
overrunning, so a generator edit more often silently reinterprets a stored
witness than deletes it. Sharper defect, same conclusion.
